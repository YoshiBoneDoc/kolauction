# Coordinated performance rollout (176–179)

No remote SQL, Cloudflare deployment, scheduler activation or bot restart is
performed by these local changes. Migration 175 is already present; do not rerun
it based on this document. Do not change the owner's QUICKSTART guide.

## Deployment order

1. Verify applied state through 175. Apply queued website SQL 176, 177, 178, 179
   in order via SQL Editor. Matching `bot/supabase/migrations/` copies are
   alternatives, never additional migrations. Move website files only after
   successful application. 176 briefly blocks bid writes while backfilling counts;
   use a quiet period. Its two-second lock deadline fails rather than queues.
2. Deploy the cache Worker (same object names and bindings). Retain existing live
   mode flags and secret. Metadata upgrades read the old combined storage format.
3. Deploy the existing `kolauction` Site Worker/frontend. Its one-minute Cron
   Trigger is configured in wrangler.jsonc; no additional Worker is created.
   Leave SITE_MAINTENANCE_ENABLED absent/false initially. Item catalogue versioned
   assets are generated by `npm run build:cloudflare`. Current catalogue syncs also
   precompute a public versioned snapshot; existing Site edge caching serves it.
4. Configure Site Worker server-side SUPABASE_URL, SUPABASE_PUBLISHABLE_KEY, and
   SITE_MAINTENANCE_TOKEN. Use a JWT with role `khub_site_maintenance`, not a
   service-role token. For projects accepting legacy HS256 JWTs,
   `scripts/createMaintenanceToken.mjs` generates a 90-day scoped token using the
   signing secret locally. Store only its output token as a Cloudflare secret;
   never put the signing secret in Cloudflare, browser variables or git. Set a
   token rotation reminder before expiry. If the project's signing configuration
   does not accept HS256, provision an equivalent supported JWT for this custom
   role before enabling maintenance; do not substitute a service-role key.
5. Confirm the deployed PostgREST version applies function `statement_timeout`
   settings (hoisted transaction settings). Supabase documents function timeouts;
   verify a disposable timeout probe under the maintenance role before activation.
   The three RPC limits are discovery 1.5s, cleanup 1s, totals 2.5s; lock waits
   are bounded to 100ms. HTTP calls allow 5s. Increasing HTTP deadlines is not a
   substitute for server-side execution limits.
6. Set SITE_MAINTENANCE_ENABLED=true. Observe scheduled Worker logs and run
   `select public.site_maintenance_status();` in SQL Editor. Discovery runs each
   minute; cleanup on minutes congruent to 2 modulo 5; totals on minute 4/34.
   Wait for all three tasks to have successful timestamps from scheduled runs.
   Check snapshot values, task duration and timeout/lock charts. If a task exceeds
   its budget, optimize it; do not increase concurrency or add a retry loop.
7. Only after those production checks, run
   `select public.activate_site_maintenance();` in SQL Editor. Activation rejects
   missing/stale task successes. It permanently makes the old bot maintenance RPC
   a no-op. Rebuild the bot normally to also skip that call based on worker status.
   Old bot versions remain safe during rollout; no second connected bot is needed.

## Failure behavior and rollback

Tasks execute in independent RPC transactions, with one nonblocking maintenance
lock distinct from financial locks. Failure retains snapshots and records task
backoff; resource failures defer all optional tasks for at least five minutes.
Transport failures also pause the Site isolate for five minutes. Cleanup deletes
at most 1,000 expired rows per run. Online counts still use their two-minute
window. Totals recompute only after relevant data changes, at most every 30
minutes. Transaction-keyed dirty markers avoid a shared source-writer lock.
No maintenance operation changes financial balances, receipts or delivery state.

The bot's fallback remains only until explicit verified activation. Afterward a
Site outage never automatically puts maintenance back into financial processing.
For rollback, disable the Site flag first; an operator can explicitly reset
`khub_bot.site_maintenance_owner.site_owned` in SQL Editor if returning ownership
to the bot is necessary. Do not run both schedulers indefinitely.

New detail clients need 177 before deployment. Legacy history RPCs are retained
for open tabs; new clients fetch 50 recent bids and use stable amount/UUID cursors
for older pages. Auction-local revisions skip unchanged active history without
re-aggregating bids; closed/admin history refreshes preserve outcome/reference
changes. Identity context has no history. Context is token-scoped; private
bidders/admin references never enter shared or persistent browser caches.
Bid counts include deletes and auction reassignment, backfill existing history,
and update transactionally under auction row locks, without a global counter.

Versioned catalogue responses use immutable caching; the small manifest is cached
for five minutes. A catalogue version disappearing during revalidation retains
the last validated browser catalogue and retries, then loads the next manifest.
Origin failures fall back to the checked-in static manifest/assets. Item eligibility
is still validated against the live database on listing/financial operations.

Source docs for timeout behavior:
https://supabase.com/docs/guides/database/postgres/timeouts
https://docs.postgrest.org/en/stable/references/transactions.html
